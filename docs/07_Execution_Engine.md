# Purpose

This document specifies the complete architecture, execution model,
runtime orchestration, lifecycle, contracts, governance,
resource management, observability, and engineering standards of
the Execution Engine.

The Execution Engine is responsible for executing approved automation
generated by the Test Generation Engine.

The Execution Engine SHALL execute automation exactly as approved by
the Decision Engine.

It SHALL NOT independently determine engineering strategy.

# 1. Purpose

The Execution Engine provides deterministic,
observable and reproducible execution of enterprise automation.

It coordinates browser sessions,
workers,
fixtures,
timeouts,
artifacts,
resource allocation,
execution state,
and runtime telemetry.

The Execution Engine transforms generated automation into
runtime execution results.

---

# 2. Scope

The Execution Engine SHALL manage

- Test execution
- Browser lifecycle
- Worker pools
- Parallel execution
- Sequential execution
- Fixture lifecycle
- Environment preparation
- Timeout management
- Resource allocation
- Artifact collection
- Runtime metrics
- Event publishing
- Execution state

The Execution Engine SHALL NOT

- Decide what should execute
- Heal failures
- Retry failures
- Generate tests
- Discover applications
- Build Knowledge Graphs
- Produce learning recommendations

Those responsibilities belong to specialized engines.

# 30A. Runtime Schedule Authority

## Purpose

This engine is the **sole runtime scheduling authority**.

That authority is expressed as **ownership of a canonical dataset** — the
**Runtime Schedule** — rather than as a prohibition on other engines. Authority
stated only as a prohibition erodes; authority backed by ownership does not.

---

## Three Artifacts, Three Owners

| Layer | Owner | Artifact | Answers |
| ----- | ----- | -------- | ------- |
| Intent | 05 | `test-plan.json` *(canonical)* | What is tested, under what constraints |
| Advice | 12 | `execution-optimization-proposal.json` *(optional)* | How to run it faster |
| **Runtime** | **07** | **`runtime-schedule.json`** *(canonical)* | What actually ran, in what order |

Ownership of an artifact SHALL NEVER imply authority over runtime execution.
12 owns a proposal; it has no scheduling authority. This engine schedules.

---

## Proposal Consumption

**Consumes the optimization proposal through the public contract defined by
`12_Adaptive_Execution_Optimizer.md` §27.**

The proposal is **optional input**, never an instruction.

```text
test-plan.json                    (required)
        │
        ├── execution-optimization-proposal.json   (optional)
        │
        ▼
Validate proposal
        │
        ├── valid    → schedule using proposal ordering
        └── invalid  → schedule using plan ordering
                       absent → schedule using plan ordering
        │
        ▼
runtime-schedule.json             (canonical, owned here)
```

---

## Proposal Validation

Before a proposal may influence scheduling, this engine SHALL verify:

| Check | Failure action |
| ----- | -------------- |
| Proposal test set **exactly equals** plan test set | Reject proposal |
| Proposal references the current plan version | Reject proposal |
| No test added, removed, or re-scoped | Reject proposal |
| No parallel group violates the plan's eligibility set (05 §26) | Reject proposal |
| Recommended timeout not below observed p99 | Reject that hint |
| Recommended workers within resource limits | Clamp to safe value |

Set equality is a mechanical comparison requiring no interpretation. A proposal
that alters *what* is validated is malformed by definition, not merely
undesirable.

A rejected proposal SHALL be logged with its reason and reported to 09. Rejection
SHALL NEVER halt execution.

---

## Null-Safety

**Execution SHALL succeed with no proposal present.**

Where the proposal is absent, rejected, or stale, this engine schedules from the
Test Plan's own ordering, which 05 §23A guarantees is complete and sufficient.

The framework SHALL remain fully functional with 12 removed entirely. This is the
property that makes optimization replaceable rather than merely described as
replaceable.

---

## Deviation Recording

This engine MAY deviate from a valid proposal for runtime safety — resource
pressure, browser instability, worker failure, or a degraded environment
(§31) — **without requesting approval**, since runtime safety is its own
authority.

Every deviation SHALL be recorded in the Runtime Schedule with:

- What was proposed
- What was executed
- Reason for deviation
- Timestamp and worker identity
- Resulting duration versus prediction

Deviations flow to **09** for reporting and **10** for learning, so proposal
quality becomes measurable. An optimizer whose proposals are never compared
against actual runtime cannot be shown to help.

---

## Run Manifest

Every execution SHALL record:

```text
(test-plan version, proposal version | null, runtime-schedule version)
```

This reproduces any execution exactly, including one in which no optimizer was
present. Determinism is preserved whether or not optimization occurred.

Persistence failures must generate alerts.

# 41. Execution Security

> **Governance only (W8 / C5).** Secret masking, credential handling, scope
> enforcement, Rules of Engagement enforcement and evidence protection. This
> engine performs **no** security testing or security scanning of the target.

The Execution Engine SHALL protect sensitive data.

Sensitive values SHALL NEVER appear in:

- Logs
- Reports
- Screenshots
- Videos
- AI Prompts
- Trace Files

Examples include:

- Passwords
- API Keys
- Tokens
- Session IDs
- Personal Data
- Financial Data

The engine shall:

- Mask secrets
- Redact credentials
- Encrypt sensitive metadata where required
- Enforce least privilege
- Validate plugin permissions

# 43. Summary

The Execution Engine is responsible for executing
approved test plans safely, efficiently, and deterministically.

It does not decide *what* to execute.

It executes the decisions produced by the Decision Engine.

Core responsibilities include:

- Resource Management
- Browser Management
- Worker Coordination
- Scheduling
- Fixture Management
- Artifact Collection
- Metrics Collection
- Failure Recovery
- Event Integration
- Execution Persistence

The engine serves as the runtime backbone of the
QA Automation Framework while preserving
deterministic, observable, and enterprise-grade execution.
